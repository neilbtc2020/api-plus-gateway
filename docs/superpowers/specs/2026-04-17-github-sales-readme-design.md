# API Plus GitHub Sales README Design

**Goal:** Replace the current GitHub showcase copy with a conversion-focused product README that drives visitors to the official website and highlights price, stability, and ongoing usability first.

**Audience:** Developers, heavy AI tool users, and prospective paying users comparing GPT/Claude access channels.

**Date Basis:** Messaging and public references aligned to information available on April 17, 2026. Public signals verified from `https://api.apiplus.cloud/` and the website's public status endpoint. Subscription card pricing is supplied by the user and should be labeled as subject to live website updates.

---

## Product Positioning

The README should present `API Plus` as a ready-to-use product, not as a technical side project and not as an upstream fork announcement.

Primary positioning:

- Unified API entry for Claude / GPT / Gemini and related workflows
- Lower-cost access with visible price and ratio advantages
- Multiple channels and fallback handling for daily usability
- Suitable for direct web use and for connecting personal AI clients/workflows

Secondary positioning:

- Product is built on top of the new-api ecosystem
- Upstream/open-source background exists, but should live near the bottom as trust context, not hero content

## Messaging Priorities

The README must answer these questions in the first screen:

1. What is this?
2. Where do I use it?
3. How much does it cost?
4. Why is it better than a generic relay or random reseller?

Priority order:

1. Official website CTA
2. Price and ratio highlights
3. Stability and channel strategy
4. Long-term usability and client compatibility
5. Community / announcement channels
6. Upstream attribution

## Main Body Structure

### Section 1: Why API Plus

Organize this section around user buying logic:

- Cheaper for sustained usage
- More stable for day-to-day work
- Easier to keep using over time

This section should translate stability into concrete user value:

- low-price and stable-price options both exist
- fallback channel switching reduces downtime risk
- announcements and handling of channel incidents improve transparency

### Section 2: What You Can Connect

This section should reduce adoption friction by showing that API Plus can plug into common AI clients and workflows.

Use product-level language, not protocol-level jargon first.

Good examples:

- can be used on the website directly
- can be connected to common AI clients and workspaces
- supports unified API usage for personal tools/scripts

Mention compatibility examples briefly and practically.

### Section 3: Why It Feels More Reliable

Translate public signals from the site into concise trust copy:

- channel differentiation
- status and announcement communication
- promo/free channels exist but paid/stable usage is separated
- users can follow QQ/TG groups for updates

Avoid overstating guarantees. Use pragmatic wording instead of absolute claims.

### Section 4: CTA and Community

Close with action-oriented links:

- official website
- QQ group
- TG group

Goal: send GitHub traffic into the live product and community channels immediately.

### Section 5: Upstream Attribution

Keep this brief and low in the page:

- built with and extended from new-api / One API ecosystem
- preserve attribution and licensing note

## Copy Rules

- Product-first, not code-first
- User value before architecture
- Prefer concrete numbers over vague claims
- Keep wording simple and sales-oriented, but not spammy
- Avoid promising absolute stability
- Avoid making the README look like a disposable "account resell" page

## Content To Remove or Demote

- Long explanations about the repo being a showcase
- Early emphasis on "based on new-api"
- Overly broad gateway feature matrices in the hero section
- Deployment-heavy language near the top
- Generic "AI asset management system" wording if it weakens conversion

## Risks and Mitigations

- **Risk:** Price information may change.
  - **Mitigation:** Add an explicit live-price disclaimer pointing to the official site.
- **Risk:** Sales tone may weaken trust with GitHub users.
  - **Mitigation:** Keep product messaging concrete and add a short upstream attribution block later in the page.
- **Risk:** Overclaiming stability.
  - **Mitigation:** Phrase stability as channel strategy, fallback handling, and transparent announcements instead of guarantees.
